# Revise Japanese Writing

## 概要

技術ドキュメント、コメント、ポリシー、ガイド、記事、解説文の日本語表現を確認し、整える。すべての技術語を機械的に翻訳するのではなく、技術的な意味と文書の論旨を保ったまま、日本語話者のメンテナが読みやすい文章にする。

このスキルは、日本語の詳細な文体基準の基準点として扱う。エージェント単位の指示ファイルでは、日本語の文体、表記、用語、句読点の詳細ルールを重複して持たず、このスキルを参照してよい。

## 手順

1. ユーザーの依頼から対象テキストを特定する。範囲が指定されていない場合は、関連する差分やファイルを確認する。
2. 普通の文章と、文字どおり保持すべき技術要素を分ける。
   - 普通の文章: 文、見出し、箇条書き、説明、ラベル。
   - 技術要素: コマンド名、ファイルパス、設定キー、コード識別子、パッケージ名、URL、例、引用値。
3. `command -v node` と `command -v npx` で Node.js と `npx` が使えるか確認する。
   - 両方使える場合は、Node.js 経由の `npx` で textlint を実行する。このスキルでは MCP サーバーは使用しないこと。
   - これは、日本語ファイルまたは書き換え対象の日本語だけを入れた一時ファイルに対して実行する。
   - 対象がファイルの場合は、次のコマンドを使う。
     `npx --yes --package textlint --package @textlint-ja/textlint-rule-preset-ai-writing --package textlint-rule-preset-ja-technical-writing textlint --rule @textlint-ja/preset-ai-writing --rule preset-ja-technical-writing <target-file>`
   - 対象がファイルになっていない文章の場合は、対象テキストだけを一時 Markdown ファイルに入れ、同じコマンドをそのファイルに対して実行する。
   - lint の指摘は自動修正ではなく、書き換えの参考として扱う。指摘が広すぎる場合でも、技術的な意味とローカルの用語を優先する。
   - lint は、AI っぽい構文、冗長さ、誇張表現、テクニカルライティング上の基本的な問題を見つけるために使う。訳語の自然さや、日本語として定着した呼び方までは判定できる前提で扱わない。
   - Node.js または `npx` が使えない場合は、その旨をユーザーに伝える。この lint 確認には Node.js と `npx` が必要である。利用できる状態になってから、lint を踏まえて確認する。
4. 関連する lint 指摘を反映しながら、普通の文章を読みやすい日本語に書き換える。
5. 技術要素は、ユーザーが明示的に変更を求めていない限り維持する。
6. リポジトリ内の既存の用語と文体に合わせる。
7. ユーザーが大きな編集を求めていない限り、文書の構成や意図を変えるような広い書き換えは避ける。
8. 長めの文章、記事、ガイド、解説文では、文単位で修正する前に、段落の構成、論の流れ、読み手の負荷、不要な演出を確認する。
9. 編集後、lint では拾いにくい語の選び方を人手で確認する。特に、直訳調の複合語、一般に定着した呼び方から外れた表現、不自然な逐語訳が残っていないかを見る。
10. 編集後、対象にした不自然な語を検索し、意図した整理が完了していることを確認する。`npx` が使えた場合は、編集後の日本語の対象に対して lint コマンドを再実行し、残った関連指摘に対応する。

## 文章表現の指針

### 原則

- 日本語で書くときは、考える段階から日本語を用いる。英語で考えてから訳すと、カタカナが多くなったり、訳文調になったりしやすい。
- 日本語は助詞の扱いが重要である。意図的な引用、ラベル、コード風の断片を除き、助詞を省略しない。
- 周囲の文体に合わせ、敬体と常体を適切に使い分ける。
- 既存文書の用語、表記、記号の使い方に合わせ、同じ概念に複数の表記を混在させない。
- lint は最低限の機械検査として使い、最終判断の代わりにはしない。語の自然さや定着した呼び方は、文脈を見て判断する。

### 技術要素の保持

文字どおり保持すべき技術要素は変更しない。

| 種類                   | 例                                                 |
| ---------------------- | -------------------------------------------------- |
| コマンド               | `mise run install`, `uv run pre-commit run -a`     |
| ファイルパス           | `docs/index.md`, `.apm/skills`                     |
| 設定キー               | `dependencies`, `interface.default_prompt`         |
| スキル名やパッケージ名 | `review-essential-code`, `suggest-commit-messages` |
| 製品名や固有名詞       | GitHub, Homebrew, Claude Code, Codex               |

### 判断基準

- その分野で一般的に通じる言葉や、日本語に該当する概念、対応する訳語が存在しない言葉は、無理に言い換えない。
- 漢語への翻訳、カタカナ表記、アルファベットのままの表記の候補がある場合は、日本語の文章として最も自然な形を選ぶ。直訳よりも、実際に定着している日本語の言い方を優先する。たとえば `hexagonal architecture` は `六角形アーキテクチャ` ではなく `ヘキサゴナルアーキテクチャ` を選ぶ。
- 訳文調にも注意する。意味は通じても、日本語の読み手が実際にはあまり使わない複合語、原文の語順や語感を引きずった逐語訳、対応づけやすさだけで選ばれた抽象語は避ける。
- 読み手と文書の目的に合わせて、専門用語、外来語、略語を使う。略語は初出時に元の用語や意味を補う。

### 文体のノイズ

- 句読点、括弧、疑問符、感嘆符などの記号は、文書内で用法を統一し、過剰に使わない。
- 情報を増やさずに丁寧そうに見せるだけの強調や姿勢の語を避ける。重要さ、深さ、包括性、意義の大きさを述べるだけではなく、具体的な中身を書く。
- AI っぽい表層表現は、機械的な禁止対象ではなく兆候として扱う。意味のない括弧、絵文字、大げさな比喩、副詞の重ね、一般論化が文書の目的に合っていない場合は取り除く。
- 直接説明すれば足りる箇所では、溜め、修辞疑問、決め台詞風の対比を使わない。強調は、論旨を明確にできる場合だけ使う。
- 主語と動詞を具体的に選ぶ。責任を持つ主体、構成要素、読み手の役割を示せる場合は、`AI`、`ツール`、`システム`、`文脈` のような広い語でぼかさない。

### 推奨語

普通の文章では読みやすい日本語を優先する。

| 元の語               | 推奨する日本語                                 |
| -------------------- | ---------------------------------------------- |
| `repository`         | `リポジトリ`                                   |
| `public repository`  | `パブリックリポジトリ` または `公開リポジトリ` |
| `private repository` | `プライベートリポジトリ`                       |
| `skill`              | `スキル`                                       |
| `task`               | `タスク`                                       |
| `shell function`     | `シェル関数`                                   |
| `shell script`       | `シェルスクリプト`                             |
| `formatter`          | `フォーマッタ`                                 |
| `editor`             | `エディタ`                                     |
| `token`              | `トークン`                                     |
| `user scope`         | `ユーザー単位`                                 |
| `project scope`      | `プロジェクト単位`                             |
| `dependency`         | `依存関係`                                     |
| `package`            | `パッケージ`                                   |
| `tag`                | `タグ`                                         |
| `commit`             | `コミット`                                     |

リポジトリ固有の好みがある場合はそれを優先する。

- ローカルの表記として定着している場合は、`ロックファイル` ではなく `lock ファイル` を使う。
- `正本` のように硬すぎたり AI っぽく見えたりする語は、より平易な語で足りるなら避ける。
- 文脈に応じて `管理元`、`置き場所`、`参照先`、`基準`、`まとめるディレクトリ`、`まとめるファイル` などを使う。
- `ポリシー文書` のように意味が重複する表現は、`ポリシー` で足りるなら短くする。

## 構成の指針

長めの文章、記事、ガイド、解説文を直すときに確認する。README の短い説明、コメント、ラベル、ポリシーでは、周囲の文書に合うものだけを使う。

### 段落と論の流れ

- 1つの段落では、1つの話題または論理の一歩だけを扱う。前提、調査、結果、評価が混ざった段落は分ける。
- 段落の最初の文で、その段落の役割がわかるようにする。前の段落との関係が自明でない場合は、接続表現で示す。
- 論は一方向に進める。必要な反論、条件、読み手の疑問を処理してから結論を置く。
- 何かを否定したり範囲を狭めたりするときは、否定する命題を明確に書き、理由を添える。`すべてが解決するわけではない` のような曖昧な否定で済ませない。

### 主張の厳密さ

- 主張の範囲を、提示した例や根拠に合わせる。例が主張の一部だけを支えるなら、主張を狭める。
- 因果を述べるときは、なぜそうなるのかを説明する。結果だけを書いて、理由を読み手に推測させない。
- 検出、保証、解決を無条件にできるかのように書かない。文脈に依存する場合は、条件付きで述べる。
- 未確認の可能性、読み手が抱きそうな疑問、登場人物の認識、反実仮想など、文に不確実性を残す理由がある場合は、その不確実性を保つ。本文内の根拠で命題が確定している場合だけ、弱い留保を削る。
- 別々の決定、原因、問題の種類を、曖昧な上位語で1つにまとめない。切り分けたうえで、どの例や道具がどの部分を支えるのかを説明する。
- 中心になる用語は、使い続ける前に定義または対象範囲を示し、その後も一貫して使う。より正確な語を導入済みなのに、`AI`、`ツール`、`文脈` のような曖昧な語へ戻らない。

### 読み手の負荷

- 後で参照しない固有名、時刻、数値、実装詳細を省き、読み手の負荷を増やさない。
- 論証の途中に前方参照を挟まない。`後の節で扱う` という注記は、現在の論が一段落した位置に置く。
- 同じ主張の繰り返しや、同じ論理的役割を持つ節を残さない。近い角度から言い直すより、1つの明確な記述にまとめる。

## 整形の指針

まず周囲の文書の形式に従う。既存のハウススタイルがない日本語の記事、書籍に近い草稿、解説 Markdown では、次の形式を既定にする。

- レビューしやすくなり、プロジェクトの形式と衝突しない場合は、一文ごとに改行する。
- コード、差分、ログ、設定ファイルの断片は fenced code block に入れる。
- 本筋を止める補足は、本文に並べず脚注へ回す。
- 太字は主に初出の定義や重要な論理上の区別に使い、装飾として使わない。
- 日本語の地の文や見出しでは、em dash、二倍ダーシ、罫線による区切りを避ける。括弧、読点、文の分割で処理する。
- 通常の日本語の並列では、固有名詞や定着した表記の一部でない限り `・` を避ける。
- 見出しは自然な1つの句にする。区切り記号で種別と主題を詰め込まない。
- 定義の列挙では、周囲の文書の言語に合わせ、英語文書では `term: explanation`、日本語文書では `用語：説明` を使う。

## 確認観点

### 共通

- 慎重な日本語話者のメンテナが最初からそう書きそうなドキュメントとして読めるか
- 不要な英語が読みやすい日本語に置き換わっているか
- 自然な日本語に必要な助詞が入っているか
- 周囲の文体、用語、表記、句読点の使い方に合っているか
- 略語、外来語、専門用語が、読み手と文書の目的に合っているか
- Node.js が使える場合、説明した `npx` の lint コマンドを日本語の対象に対して実行したか
- 文書の意図を崩すほど広い提案は避けつつ、関連する lint 指摘を反映したか

### 用語と技術要素

- 原語を機械的に当てただけの不自然な複合語、英語の説明をなぞった言い回し、一般的な呼び方から外れた訳語が残っていないか
- 漢語訳、カタカナ、アルファベットの候補がある中で、日本語として最も自然な表記を選べているか
- コマンド、パス、識別子、設定キー、例が正確に残っているか
- 表現変更によって技術的な意味が変わっていないか
- 編集したファイル間で用語が揃っているか
- 固有名詞やコード風の文字列まで誤って置き換えていないか

### 長文と論証

- 長めの文章では、各段落が論理の一歩を明確に進めているか
- 主張、例、条件、因果の説明が対応しているか
- 必要な不確実性を保ちつつ、根拠のない弱い留保だけを取り除けているか
- 別々の原因、決定、問題の種類を曖昧な上位語にまとめず、切り分けているか
- 中身のない強調、過剰な演出、曖昧な主体、冗長な要約文を取り除けているか
- 整形の判断では、長文向けの既定よりも対象文書のローカルな形式を優先したか

## 参考資料

このスキルの作成や保守で参考にした文献、関連スキル、Web ページは `references/background.md` に記載する。

## 出力

ファイルを編集した場合は、最後にどの種類の表記を変更したかを簡潔にまとめる。編集が不要な場合は、文章がすでに十分読みやすいことと、意図的に維持した用語を伝える。
