# Revise Japanese Writing

## 概要

技術ドキュメント、コメント、ポリシー、ガイド、記事、解説文の日本語表現を整える。技術的な意味と論旨を保ち、日本語話者のメンテナが読みやすい文章にする。

このスキルを日本語の詳細な文体基準とする。エージェント向けの指示では、同じルールを重複して持たず、このスキルを参照してよい。

## 手順

1. 依頼から対象テキストを特定する。範囲がなければ関連する差分やファイルを確認する。
2. 普通の文章と、文字どおり保持すべき技術要素を分ける。
   - 普通の文章: 文、見出し、箇条書き、説明、ラベル。
   - 技術要素: コマンド名、ファイルパス、設定キー、コード識別子、パッケージ名、URL、例、引用値。
3. 普通の文章を読みやすい日本語に書き換える。技術要素は明示的な依頼がない限り維持する。
4. リポジトリ内の既存の用語と文体に合わせる。
5. ユーザーが大きな編集を求めていない限り、文書の構成や意図を変えるような広い書き換えは避ける。
6. 長めの文章、記事、ガイド、解説文では、文単位で修正する前に、段落の構成、論の流れ、読み手の負荷、不要な演出を確認する。
7. 編集後、用語を見直し、対象にした不自然な語を検索して整理が完了していることを確認する。

## 文章表現の指針

### 原則

- 日本語で書くときは、考える段階から日本語を用いる。英語で考えてから訳すと、カタカナが多くなったり、訳文調になったりしやすい。
- 日本語は助詞の扱いが重要である。意図的な引用、ラベル、コード風の断片を除き、助詞を省略しない。
- 周囲の文体に合わせ、敬体と常体を適切に使い分ける。
- 既存文書の用語、表記、記号の使い方に合わせ、同じ概念に複数の表記を混在させない。
- 文体確認は美しさの採点ではなく、欠陥の検出として扱う。曖昧さ、不一致、訳文調、読者の誤解につながる具体的なリスクを指摘し、美しさ、味わい、品格を判定できるとは書かない。

### 技術要素の保持

文字どおり保持すべき技術要素は変更しない。

| 種類                   | 例                                                 |
| ---------------------- | -------------------------------------------------- |
| コマンド               | `mise run install`, `uv run pre-commit run -a`     |
| ファイルパス           | `docs/index.md`, `.apm/skills`                     |
| 設定キー               | `dependencies`, `interface.default_prompt`         |
| スキル名やパッケージ名 | `review-essential-code`, `suggest-commit-messages` |
| 製品名や固有名詞       | GitHub, Homebrew, Claude Code, Codex               |

### 判断基準

- その分野で一般的に通じる言葉や、日本語に該当する概念、対応する訳語が存在しない言葉は、無理に言い換えない。
- 漢語への翻訳、カタカナ表記、アルファベットのままの表記の候補がある場合は、日本語の文章として最も自然な形を選ぶ。直訳よりも、実際に定着している日本語の言い方を優先する。たとえば `hexagonal architecture` は `六角形アーキテクチャ` ではなく `ヘキサゴナルアーキテクチャ` を選ぶ。
- 日本語の読み手が使わない訳文調や造語的な複合語は使わない。たとえば `鍵語` ではなく `重要な用語` と表現し、`基礎チェック` のように名詞を連結した表現が造語的である場合は `基礎的なチェック` とする。
- 並列する語で共通する中心語を省き、読み手に補わせない。たとえば `単体、結合、E2E の各テスト` ではなく、`単体テスト、結合テスト、E2E テスト` と書く。
- 出典、日本語版の書籍、プロジェクトの用語集で確立している技術用語は、短く見えることだけを理由に展開しない。たとえば、出典で定着している `共有依存`、`揮発性依存`、`協力オブジェクト` はそのまま使う。
- カルク (calque) が疑われる場合は、日本語の表現が英語の慣用句、比喩、特徴的な構文をなぞっていないかを見る。なぞっている場合は英語の形を捨て、日本語として選び直す。ただし、普通の文法や定着した外来語までカルクとして扱わない。
- 読み手と文書の目的に合わせて、専門用語、外来語、略語を使う。略語は初出時に元の用語や意味を補う。
- 文に必要な品詞を保つ。英単語を組み合わせた用語は、略すと意味や品詞が曖昧になる場合は略さない。たとえば `squash merge` の方法や完了状態を指すなら、`スカッシュ` ではなく `スカッシュマージ`、`スカッシュマージ済み`、または意味が明確な日本語表現を使う。

### 文体のノイズ

- 1つの概念には1つの名称を使う。繰り返しを避けるためだけに重要な用語を言い換えたり、別々の概念を同じ曖昧な語でまとめたりしない。重要な用語の反復そのものを問題にせず、重複した情報を減らす。
- 情報を増やさずに丁寧そうに見せるだけの強調や姿勢の語は、原則使わない。重要さ、深さ、包括性、意義の大きさを述べるだけではなく、具体的な中身を書く。
- AI っぽい表層表現は、機械的な禁止対象ではなく兆候として扱う。意味のない括弧、絵文字、大げさな比喩、副詞の重ね、一般論化が文書の目的に合っていない場合は取り除く。
- 直接説明すれば足りる箇所では、溜め、修辞疑問、決め台詞風の対比を使わない。強調は、論旨を明確にできる場合だけ使う。
- 主語と動詞を具体的に選ぶ。責任を持つ主体、構成要素、読み手の役割を示せる場合は、`AI`、`ツール`、`システム`、`文脈` のような広義な言葉でごまかさない。
- `正本` のような内部用語は説明なしに使わない。原則として一般的な言葉に置き換える。
- `効く`、`刺さる`、`回す` のような比喩的な動詞は使わない。
- `これにより`、`〜することが可能です`、`〜が求められます` のような英語直訳調の定型句は使わない。

### 推奨語

普通の文章では読みやすい日本語を優先する。

| 元の語               | 推奨する日本語                                 |
| -------------------- | ---------------------------------------------- |
| `repository`         | `リポジトリ`                                   |
| `public repository`  | `パブリックリポジトリ` または `公開リポジトリ` |
| `private repository` | `プライベートリポジトリ`                       |
| `skill`              | `スキル`                                       |
| `task`               | `タスク`                                       |
| `shell function`     | `シェル関数`                                   |
| `shell script`       | `シェルスクリプト`                             |
| `formatter`          | `フォーマッタ`                                 |
| `editor`             | `エディタ`                                     |
| `token`              | `トークン`                                     |
| `user scope`         | `ユーザー単位`                                 |
| `project scope`      | `プロジェクト単位`                             |
| `dependency`         | `依存関係`                                     |
| `production code`    | `プロダクションコード`                         |
| `package`            | `パッケージ`                                   |
| `tag`                | `タグ`                                         |
| `commit`             | `コミット`                                     |

リポジトリ固有の好みがある場合はそれを優先する。

- ローカルの表記として定着している場合は、`ロックファイル` ではなく `lock ファイル` を使う。
- 文脈に応じて `管理元`、`置き場所`、`参照先`、`基準`、`まとめるディレクトリ`、`まとめるファイル` などを使う。
- `ポリシー文書` のように意味が重複する表現は、`ポリシー` で足りるなら短くする。

## 構成の指針

長めの文章、記事、ガイド、解説文を直すときに確認する。README の短い説明、コメント、ラベル、ポリシーでは、周囲の文書に合うものだけを使う。

### 段落と論の流れ

- 1つの段落では、1つの話題または論理の一歩だけを扱う。前提、調査、結果、評価が混ざった段落は分け、段落の役割と前段落との関係を明確にする。
- 論は一方向に進める。必要な反論、条件、読み手の疑問を処理してから結論を置く。
- 1つの文では、解釈を1通りへ絞る。長い文を機械的な欠陥とは見なさず、修飾の範囲、主述の対応、省略された主語によって複数の読みが成り立つ場合に書き換える。
- 何かを否定したり範囲を狭めたりするときは、否定する命題を明確に書き、理由を添える。`すべてが解決するわけではない` のような曖昧な否定で済ませない。

### 主張の厳密さ

- 主張の範囲を根拠に合わせる。主張と根拠は意味でつなげ、因果を述べるときは仕組みも説明する。
- 因果と相関を混同せず、比較や分類の基準を明確にする。別々の決定、原因、問題の種類は分けて扱う。
- 検出、保証、解決を無条件に約束しない。不確実性を残す理由がある場合は保ち、本文で裏付けられる弱い留保だけを削る。
- 中心になる用語は、定義または対象範囲を示してから一貫して使う。より正確な語を導入した後に、`AI`、`ツール`、`文脈` のような曖昧な語へ戻らない。

### 読み手の負荷

- 後で参照しない固有名、時刻、数値、実装の詳細を省き、読み手の負荷を増やさない。
- 論証の途中に前方参照を挟まない。`後の節で扱う` という注記は、現在の論が一段落した位置に置く。
- 同じ主張の繰り返しや、同じ論理的役割を持つ節を残さない。近い角度から言い直すより、1つの明確な記述にまとめる。

## 整形の指針

まず周囲の文書の形式に従う。既存のハウススタイルがない日本語の記事、書籍に近い草稿、解説 Markdown では、次の形式を既定にする。

- 改行は、レビューしやすくなりプロジェクトの形式と衝突しない場合に限り、文または意味のまとまりの境界へ置く。文字数をそろえるためだけに本文を折り返さない。
- コード、差分、ログ、設定ファイルの断片は fenced code block に入れる。
- 本筋を止める補足は、本文に並べず脚注へ回す。
- 太字は主に初出の定義や重要な論理上の区別に使い、装飾として使わない。
- 日本語の地の文や見出しでは、em dash、二倍ダーシ、罫線による区切りは原則使わない。括弧、読点、文の分割で処理する。
- 通常の日本語の並列では、固有名詞や定着した表記の一部でない限り `・` は原則使わない。
- 見出しは自然な1つの句にする。区切り記号で種別と主題を詰め込まない。
- 定義の列挙では、周囲の文書の言語に合わせ、英語文書では `term: explanation`、日本語文書では `用語：説明` を使う。

## 確認観点

### 共通

- 慎重な日本語話者のメンテナが最初からそう書きそうな文書として読め、助詞の使い方、日本語への言い換え、外来語、略語、専門用語が自然か
- 周囲の文体、用語、表記、句読点の使い方に合っているか

### 用語と技術要素

- 不自然な複合語や英語をなぞった表現がなく、定着した用語、技術要素、固有名詞、コード風の文字列を正確に保てているか
- 編集したファイル間で重要な概念と繰り返す用語が揃い、曖昧な略語、不要な言い換え、広すぎる語を避けているか
- 表現変更によって技術的な意味が変わっていないか

### 長文と論証

- 各段落が論理の一歩を明確に進め、主張、根拠、条件、比較、因果の説明が対応しているか
- 必要な不確実性を保ち、別々の原因や決定を切り分け、中身のない強調、過剰な演出、曖昧な主体、冗長な要約文を取り除けているか
- 整形では対象文書のローカルな形式を優先し、改行を任意の文字数ではなく文または意味のまとまりの境界に置いているか

## 出力

ファイルを編集した場合は、最後にどの種類の表記を変更したかを簡潔にまとめる。編集が不要な場合は、文章がすでに十分読みやすいことと、意図的に維持した用語を伝える。
