# 結合テストの指針

## 境界と依存関係

問題となる連携上の振る舞いとリスクを示してから、エントリーポイント、含めるコンポーネント、プロセス外の依存関係、除外する対象、観測する結果を定める。
保証範囲をその境界より広げない。

依存関係は、技術の種類や組織上の所有関係だけでなく、問題となるリスクに対して果たす役割で分類する。

- 依存関係の振る舞いや契約が保証対象に含まれ、影響を閉じ込められる場合は、実物を使う。
- 実際の影響が危険、利用できない、または保証対象外の場合は、制御するか置き換える。
- 代替手段で本番の重要な振る舞いを再現できない場合は、残る問題を記録する。

管理下の依存関係と管理外の依存関係は、プロジェクトで使われている場合に役立つ用語であり、必須の分類ではない。
ベンダー、プロトコル、トランザクション、クエリ、永続化の振る舞いが問題となる場合は、本番で使う製品と、リスクに関係する設定上の性質を保つ。

通信自体に外部から見える意味がある場合だけ、やり取りを検証する。
内部の協力オブジェクトを連鎖的にモックせず、外部システムに最も近い自分たちの境界を観測する。

## シナリオと状態

重要な連携を通る代表的な成功経路から始める。
制約、トランザクションの境界、シリアライズの不整合、アダプタの変換、インフラに固有の順序、フレームワークの設定など、実際の連携に依存する失敗ケースを追加する。
組み合わせが多いドメイン上のケースは、可能なら狭いテストで扱う。

各テストは必要な状態を自分で用意し、実行順の影響を受けないようにする。
本番環境を再現できている度合いとコストに応じて、状態を分離する方法を選ぶ。
次のような方法がある。

- テストごとに固有のデータを使う
- 実行前に状態を消去する
- 名前空間を分ける
- 使い捨て環境を使う

成功後にしか動かない後始末だけに依存しない。

業務上重要な入力はテスト内で見えるようにする。
技術的な準備にはヘルパーを使ってよいが、シナリオを隠さない。

## 実装とレビュー

- 準備にかかるコストを減らすために無関係な確認をまとめず、一まとまりのシナリオを扱う。
- プロダクションコードのロジックを再現せず、意味のある出力、永続化状態、境界の契約を検証する。
- 固定時間の待機ではなく、条件に基づく上限付きの待機を使う。
- 環境、準備、プロダクト、観測方法のどこで失敗したかを区別する。
- 失敗した境界を特定できる情報を残す。

実物の依存関係を使えない場合は、有用な狭いテストを残し、確認できない範囲を明示する。
