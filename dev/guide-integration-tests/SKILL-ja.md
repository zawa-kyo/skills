# 結合テストを設計する

## 責務

連携上のリスクを、そのリスクを表面化させる実際の連携を含むテストへ落とし込む。
環境を制御し、失敗した境界を特定できるようにする。
テストスイート全体の構成はここで決めない。
ユーザーからの明確な依頼または `guide-automated-tests` が作成したテスト課題を起点にする。

クラス数や一律の分類で結合テストを定義せず、実際のエントリーポイント、含めるコンポーネント、プロセス外の依存関係、観測する結果を表す。

## 手順

1. 振る舞い、問題となる連携上の失敗、実際の連携に依存する根拠を確認する。
2. プロダクションコードの境界、アダプタ、インフラ、外部システムとの契約、既存のテスト、利用できる環境を調べる。
3. 所有関係、再現度、実行時間、分離方法によって境界が一意に決まらない場合は、妥当な選択肢を比較する。
4. 実物のまま使う、制御する、置き換える、利用できないものとして記録する依存関係を決める。
5. 代表的なシナリオ、独立した状態、意味のある観測方法を設計する。
6. リポジトリの規約に従って実装し、得られる信頼性、再現度、原因調査、実行時間、保守コストを確認する。

指定された境界では問題となる仕組みを含められない場合は、残る問題を説明する。
`guide-automated-tests` を利用できる場合はテストレベル間の判断を戻し、利用できない場合は見直す点を示す。
テストの目的となる仕組みを代替物で取り除かない。

依存関係、シナリオ、実装、レビューに関する固有の指針は `references-ja/guidance.md` を読む。
英語で出力する場合や英語文書を扱う場合は `references/guidance.md` を使う。

## レビュー

実際に通る仕組み、保証範囲、状態の独立性、観測方法、環境コストに関する具体的な問題から報告する。

単体テストより遅いことや、プロジェクトに固有の境界の名称を使っていることだけを問題にしない。

## 出力

振る舞いと連携上のリスク、確認した状況、選んだ境界、依存関係の扱いを報告する。
シナリオ、状態の管理方法、観測方法、実行した確認、残るリスクも示す。
重要な仮定と、ユーザーと検討した選択肢も示す。

ユーザーから指定がない限り、ユーザーが使った言語で出力する。
