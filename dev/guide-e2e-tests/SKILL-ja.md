# E2E テストを設計する

## 責務

システム全体または利用者から見えるリスクを、少数の代表的で、制御でき、信頼できる一連のテストへ落とし込む。
テストスイート全体の構成はここで決めず、狭い境界ですでに守られている詳細なケースを繰り返さない。
`guide-automated-tests` が作成したテスト課題を起点にする。

E2E テストは、プロジェクトが定める信頼性の境界として扱う。
デプロイ済み環境、別に起動したシステム全体、外部から操作する別の構成などがあり得る。
名前だけで判断せず、実際に含める範囲を示す。

## 手順

1. 利用者から見える振る舞いと、検出すべきシステム全体の失敗を確認する。
2. エントリーポイント、システムの構成、外部の依存関係、認証、データの所有者、観測手段、既存のテスト、プロジェクトの E2E テストに関する規約を調べる。
3. 想定するアーキテクチャや E2E テストの境界が明らかでない場合は、妥当な解釈を示してユーザーと確認する。
4. 一連のテストが通る境界、含めるシステム、制御または利用できない依存関係、正当に保証できる範囲を定める。
5. 少数の重要な代表シナリオまたはスモークテストを選ぶ。
6. 対応しているインターフェースを通して、管理できる状態、観測可能な完了条件、意味のある結果、失敗時の情報を備えたテストを実装する。
7. E2E テストでしか得られない信頼性、本番環境を再現できている度合い、テスト間の分離、不安定さ、原因調査、実行時間、後始末を確認する。

狭い境界で同じ信頼をより低いコストで得られる場合は、その選択肢を説明する。
テストレベル間の責務分担は、`guide-automated-tests` で見直す。

シナリオ、環境、信頼性、レビューに関する固有の指針は `references-ja/guidance.md` を読む。
英語で出力する場合や英語文書を扱う場合は `references/guidance.md` を使う。

## レビュー

信頼性や安定性に影響する具体的な問題から報告する。
機能カバレッジを増やすことだけを理由にシナリオを追加せず、プロジェクトの境界が本番と同じようにデプロイされていないことだけを問題にしない。

## 出力

一連の振る舞いとリスク、確認した状況、実際の E2E テストの境界、除外する依存関係、状態と後始末、完了条件、期待する結果、失敗時の情報、実行した確認、残る問題を報告する。
重要な仮定と、ユーザーと比較した選択肢も示す。

ユーザーから指定がない限り、ユーザーが使った言語で出力する。
