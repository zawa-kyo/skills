# ルール整理メモ

このファイルは、ルールを追加、修正、削除するときの保守用メモである。
スキルの実行時に読む資料ではなく、どの工程にどの判断を置くかを確認するために使う。

参照元や採用判断の理由は `sources.md` にまとめる。
このファイルには、参照元 ID や細かな資料対応を入れない。

## 書き方

ルールを追加するときは、次の観点で書く。

- 工程: そのルールを置くワークフロー上の位置。
- 適用場面: そのルールが必要になる状況。
- 置き場所: そのルールを記載する実行時資料。
- 優先度: Essential / Recommended / Suggested。
- 判断内容: 利用者に伝えるルールの要点。
- 例外や注意点: 例外を認める条件や、誤用しやすい点。

## 目的

置き場所: `references/01-purpose.md`。

優先度: Essential。

単体テストは、テスト数やカバレッジの最大化ではなく、持続可能な変更を支えるために書く。
価値の低いテストは、改善するか、別のテスト種別へ移すか、削除する。

## 文脈

置き場所: `references/02-context.md`。

優先度: Essential。

プロジェクトのコードに対してテストを設計する前に、ドメイン、アーキテクチャ、依存関係、既存テストの文脈を必要な範囲で読む。
価値のある振る舞いがテストしにくい場合は設計問題の手がかりになるが、すべての難しさがドメインモデルの問題を示すわけではない。

## テスト戦略

置き場所: `references/03-test-strategy.md`。

優先度: Essential。

テスト対象の単位は、クラス構造ではなく振る舞いで決める。
高速に実行でき、共有依存や不安定な依存から切り離されているなら、1つの振る舞いが複数クラスにまたがってもよい。

## テスト設計

置き場所: `references/04-test-design.md`。

優先度: Essential。

実装詳細ではなく、外から確認できる結果を優先して検証する。
意味のある境界通信だけを検証し、スタブは検証しない。

## 実装

置き場所: `references/05-implementation.md`。

優先度: Recommended。

テストは Arrange、Act、Assert を軸に構成する。
テスト専用の本番コード変更は避け、本番モデルも改善するリファクタリングを優先する。

## セルフレビュー

置き場所: `references/06-self-review.md`。

優先度: Essential。

目的、文脈、戦略、設計、実装という同じワークフローに沿ってテストをレビューする。
レビュー依頼では、別のチェックリストへ切り替えず、ワークフローを圧縮して使う。
