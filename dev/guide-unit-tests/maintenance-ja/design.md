# 設計

## モチベーション

自動テストは、書けば必ず資産になるわけではない。
価値の低い振る舞いをテストしたり、実装詳細に強く依存したり、本番ロジックをテスト側に複製したりすると、テストはプロダクトの成長を支えるどころか負債になる。

このスキルは、単体テストを書くこと自体を目的にせず、正しいテストを書くためのものである。
まず「なぜこのテストが必要なのか」を確認し、守るべき振る舞い、リスク、単体テストの境界、観測方法を順に決める。
そのうえで、テストコードの形やテストダブルの使い方を選択する。
この順序をガードレールにすることで、単体テストをカバレッジ向上の作業ではなく、設計と保守を支えるプラクティスとして扱う。

## 主な参照文献

主たる参照文献は Vladimir Khorikov の _Unit Testing: Principles, Practices, and Patterns_ である。ただし、このスキルは同書だけに依存しない。
その他の書籍、チームごとのプラクティス、言語ごとの制約、実プロジェクトから得た知見も取り込めるようにしておく。

## 設計方針

このスキルは、参照元の章、特定の学派、個別ユースケースではなく、単体テストを設計、実装、レビューするときの思考順序で整理する。

| 工程           | 資料                   | 役割                                                                 |
| -------------- | ---------------------- | -------------------------------------------------------------------- |
| 目的           | `01-purpose.md`        | テストが存在すべき理由と守るリスクを扱う。                           |
| コンテキスト   | `02-context.md`        | ドメイン、アーキテクチャ、依存関係、既存テストのコンテキストを扱う。 |
| テスト戦略     | `03-test-strategy.md`  | テストレベル、単体テストの境界、依存関係の扱い、検証方法を扱う。     |
| テスト設計     | `04-test-design.md`    | 具体的なケース、アサーション、テストダブルの役割を扱う。             |
| 実装           | `05-implementation.md` | テストコードの形と安全なテスタビリティ改善を扱う。                   |
| セルフレビュー | `06-self-review.md`    | セルフレビューとレビュー依頼時の圧縮フローを扱う。                   |

この構成にしておくと、新しい資料は既存ルールを補足したり、修正したりする形で取り込める。
章ごとの要約やユースケース別の資料を並列に増やさない。

レビューは、このスキルから独立した分岐ではない。
目的を推定し、必要なコンテキストを読み、戦略を確認し、具体的なアサーションと実装品質を見てから指摘するという同じ流れを圧縮して使う。

## 実行時資料と保守資料

`references/` と `references-ja/` は、このスキルを使うときに読む実行時資料である。
単体テストの作成、レビュー、境界の選定、アサーション方針、設計フィードバックで参照する。
実行時に必要なルール、確認項目、優先度、トレードオフに絞り、出典対応や Rule ID の台帳にはしない。

`maintenance/` と `maintenance-ja/` は、このスキルを保守するときに読む資料である。
通常の単体テストの補助としては参照しない。
このスキルを編集する、ルール構造を変える、参照元との対応を追う場合に使う。
設計の見直しや Rule ID、優先度の議論にも使う。

日英で対応するファイルは、ファイル名と意味を揃える。
英語版と日本語版を逐語訳にする必要はない。
ただし、実行時ルールと保守用メタ情報の意味は一致させる。

`references/example.md` を追加するときは、同じ変更で `references-ja/example.md` も追加する。
`maintenance/example.md` を追加するときは、同じ変更で `maintenance-ja/example.md` も追加する。

## 参照元の管理

参照元との対応、Rule ID、採用した論点、採用しなかった論点、保留中の疑問は `maintenance/sources.md` に記録する。
実行時資料には、書籍の索引、参照元対応、Rule ID の台帳を入れない。
