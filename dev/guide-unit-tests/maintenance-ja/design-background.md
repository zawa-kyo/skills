# 設計背景

## このスキルを作る理由

このスキルは、単体テストをカバレッジ向上の手段だけでなく、設計と保守を支える実践として扱うために作る。

単体テストは、重要な振る舞いを少ない保守コストで守れるときに価値を持つ。
一方で、実装詳細に強く依存するテストは負担になる。
モックの過剰な使用、本番ロジックの複製、通常のリファクタリングを難しくするテストも同じである。

## 最初に参照した資料

最初に参照した資料は Vladimir Khorikov の _Unit Testing: Principles, Practices, and Patterns_ である。
この本は、テストの価値、リファクタリング耐性、外から確認できる振る舞い、テストダブルを整理するうえで役に立つ。
出力・状態・相互作用テストのトレードオフを考えるうえでも参考になる。

ただし、このスキルは同書だけに依存しない。
他の書籍、チームの実践、言語ごとの制約、実プロジェクトから得た知見も取り込めるようにしておく。

## 設計判断

このスキルは、参照元の章、特定の学派、個別ユースケースではなく、単体テストを設計、実装、レビューするときの思考順序で整理する。

- `01-purpose.md` は、テストが存在すべき理由と守るリスクを扱う。
- `02-context.md` は、ドメイン、アーキテクチャ、依存関係、既存テストの文脈を扱う。
- `03-test-strategy.md` は、テストレベル、単体テストの境界、依存関係の扱い、検証方法を扱う。
- `04-test-design.md` は、具体的なケース、アサーション、テストダブルの役割を扱う。
- `05-implementation.md` は、テストコードの形と安全なテスタビリティ改善を扱う。
- `06-self-review.md` は、セルフレビューとレビュー依頼時の圧縮フローを扱う。

この構成にしておくと、新しい資料は既存ルールを補足したり、修正したりする形で取り込める。
章ごとの要約やユースケース別の資料を並列に増やさない。

レビューは、このスキルから独立した分岐ではない。
目的を推定し、必要な文脈を読み、戦略を確認し、具体的なアサーションと実装品質を見てから指摘するという同じ流れを圧縮して使う。

## 実行時資料と保守資料

`references/` と `references-ja/` は、このスキルを使うときに読む実行時資料である。
単体テストの作成、レビュー、境界選定、アサーション方針、設計フィードバックで参照する。

`maintenance/` と `maintenance-ja/` は、このスキルを保守するときに読む資料である。
通常の単体テスト支援では読まない。
このスキルを編集する、ルール構造を変える、参照元との対応を追う、設計背景を見直す場合に使う。

日英で対応するファイルは、ファイル名と意味を揃える。
英語版と日本語版を逐語訳にする必要はない。
ただし、ルール、優先度、適用条件、例外の内容は一致させる。

`references/example.md` を追加するときは、同じ変更で `references-ja/example.md` も追加する。
`maintenance/example.md` を追加するときは、同じ変更で `maintenance-ja/example.md` も追加する。

## 参照元の管理

参照元との対応、採用した論点、採用しなかった論点、保留中の疑問は `maintenance/sources.md` に記録する。
実行時資料には、書籍の索引のような情報を入れない。
