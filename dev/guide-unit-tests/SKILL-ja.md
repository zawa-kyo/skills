# 単体テストを設計する

## 責務

振る舞いとリスクを、高速かつ結果が決定的な単体テストへ落とし込む。
テストはほかのテストから独立させ、実装の詳細へ不要に結合させない。
テストスイート全体の構成はここで決めない。
ユーザーからの明確な依頼または `guide-automated-tests` が作成したテスト課題を起点にする。

## 既存設計を尊重する

単体テストの境界を決める前に、プロダクションコード、ドメインの用語、依存関係、アーキテクチャ、既存のテストを確認する。
確立されたアーキテクチャがテスト対象の振る舞いに合っている場合は、その設計に従う。

アーキテクチャや設計意図が明らかでない場合は、次の順に進める。

1. コードから読み取れる構造と責務を説明する。
2. 根拠と解釈を分ける。
3. 解釈の違いがテスト境界やリファクタリング案に与える影響を説明する。
4. 影響の大きな仮定はユーザーと確認する。

より明確な設計がない場合は、判断と副作用を分けるクリーンアーキテクチャ、レイヤードアーキテクチャ、オニオンアーキテクチャの考え方を出発点にしてよい。
現状の設計に一貫性がある場合や、テストのために必要な範囲を超える場合は、その構造への書き換えを求めない。

## 手順

1. 振る舞い、リグレッションのリスク、単体テストで守れると考える理由を確認する。
2. 意図された責務を理解できる範囲で、プロダクションコードと既存のテストを調べる。
3. 振る舞いの境界、実物のまま使う依存関係と制御する依存関係、観測方法を決める。
4. 意味のある入力と期待結果を持つ少数の具体的なケースを設計する。
5. テストダブルの役割を明確にし、リポジトリの規約に従って実装する。
6. 振る舞いの保護、リファクタリングへの耐性、決定性、読みやすさ、保守コストを確認する。

依存関係を制御すると問題となる仕組み自体がなくなる場合は、残る問題を説明する。
`guide-automated-tests` を利用できる場合はテストレベル間の判断を戻し、利用できない場合は見直す必要がある判断を示す。

境界、依存関係、ケース、実装、レビューに関する単体テスト固有の指針は `references-ja/guidance.md` を読む。
英語で出力する場合や英語文書を扱う場合は `references/guidance.md` を使う。

## レビュー

振る舞い、得られる信頼性、リファクタリングへの耐性、決定性、読みやすさ、保守性に影響する問題から報告する。
テストの流派に関する好みや、リポジトリで採用されている書式の違いだけを問題にしない。

## 出力

振る舞いとリスク、確認した状況、ユーザーと確認したアーキテクチャ上の仮定、選んだ境界、依存関係の扱いを報告する。
観測方法、ケース、実装の変更、実行した確認、残るリスクも示す。詳しさはタスクに合わせる。

ユーザーから指定がない限り、ユーザーが使った言語で出力する。
