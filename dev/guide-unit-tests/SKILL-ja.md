# 単体テストガイド

## 概要

このスキルは、単体テストを実装するときとレビューするときの両方で使う。
目的は、テスト数やカバレッジを最大化することではない。
重要な振る舞いを、無理のない保守コストで守り、コードベースを変更しやすい状態に保つことである。

このスキルは、単体テストの作成、単体テストのレビュー、ある振る舞いを単体テストで扱うべきかの判断、テストしにくさから設計改善を考える場面で使う。

## 対象範囲

このスキルは次の用途に使う。

- 価値の高い単体テスト対象を選ぶ
- どの振る舞いを確認し、何を検証するか決める
- 出力、状態、相互作用のどれを検証するか選ぶ
- テストダブル、スタブ、モックを使い分ける
- 読みやすいテスト名、セットアップ、実行、アサーションを書く
- 壊れやすいテスト、過剰指定のテスト、価値の低いテストをレビューする
- 単体テストしにくいコードから設計改善の手がかりを見つける

結合テスト、E2E テスト、データベーステスト、CI、カバレッジツール、テストフレームワーク API の詳細設定は、このスキルの対象外である。
それらには、単体テストの境界を説明するために必要な範囲でだけ触れる。

## 参照資料の選び方

必要な参照資料だけを読む。

| 状況                                              | 読むファイル                               |
| ------------------------------------------------- | ------------------------------------------ |
| 目的、品質基準、優先度、用語が必要                | `references-ja/foundations.md`             |
| 何を単体テストにするか決めたい                    | `references-ja/test-target-selection.md`   |
| 何を検証するか、モックやスタブをどう使うか決めたい | `references-ja/observation-and-oracles.md` |
| テストコードの構造を書きたい、または改善したい    | `references-ja/test-construction.md`       |
| コードが単体テストしにくく、設計問題が疑われる    | `references-ja/design-feedback.md`         |
| テストやテストしやすさのレビューを依頼された      | `references-ja/review-heuristics.md`       |
| このスキルの設計背景を確認したい                  | `references-ja/design-background.md`       |

英語で出力する場合や英語文書を編集する場合は、対応する `references/` 側のファイルを使う。
このスキルを編集するときは、`references/` と `references-ja/` の意味を揃える。

## ワークフロー

1. 依頼を、テスト作成、テストレビュー、境界選定、アサーション方針、設計フィードバックのどれかに分類する。
2. 詳細な助言を出す前に、該当する参照ファイルを読む。
3. クラス名、メソッド名、モック、アサーションを先に決めず、ユーザーが守りたい振る舞いを特定する。
4. 実装詳細に結び付いたテストより、外から確認できる振る舞いを優先する。
5. 価値が低いテストや保守しにくいテストは、資産ではなく技術負債として扱う。
6. 例外があるルールでは、普遍的な規則として断定せず、適用条件とトレードオフを説明する。
7. 論点が単体テストの範囲を超える場合は、単体テストの境界と、別のテスト種別や設計作業で扱うべき範囲を明確にする。

## 出力

新しいテストを書くときは、次を示す。

- テストすべき振る舞い
- 推奨するテスト境界
- 優先する確認方法
- 書くべきテストケース
- テストを簡単にする設計変更

レビューでは、実際に問題がある場合は指摘事項から始める。
違反しているルール、リスク、最小限の有効な修正方針を含める。
重大な問題がない場合は、その旨を明確に伝え、確認しきれていない前提や未検証の点があれば述べる。

ユーザーが別言語を明示しない限り、ユーザーの依頼言語で出力する。
