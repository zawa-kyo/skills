# 単体テストガイド

## 概要

このスキルは、単体テストを設計、実装、レビューするときに使う。
目的は、テスト数やカバレッジを最大化することではない。
重要な振る舞いを、無理のない保守コストで守り、コードベースを変更しやすい状態に保つことである。

このスキルは、トピックの索引ではなく、思考を進めるためのワークフローとして扱う。
抽象的な目的から具体的な実装へ進み、最後に最初の目的へ戻って結果を確認する。

## 対象範囲

このスキルは次の用途に使う。

- テスト依頼を、目的とリスクへ変換する
- 一般論だけのテストを避けるため、必要なドメインとアーキテクチャの文脈を読む
- テストコードを書く前に、単体テスト戦略を設計する
- 具体的なテストケース、アサーション、テストダブルの役割を決める
- 読みやすいテストを実装し、必要ならテストしにくい本番コードをリファクタリングする
- 目的、文脈、戦略、設計、実装の整合性からテストをレビューする

結合テスト、E2E テスト、データベーステスト、CI、カバレッジツール、テストフレームワーク API の詳細設定は、このスキルの対象外である。
それらには、単体テストの境界を説明するために必要な範囲でだけ触れる。

## 基本ワークフロー

依頼が狭いレビューや小さな局所変更でない限り、ワークフロー順に進める。
圧縮する場合でも、目的、振る舞い、境界の確認は省略しない。

1. 目的を定める: 守る振る舞い、リスク、保守上の目的を特定する。カバレッジ起点の依頼は、テストが存在すべき具体的な理由へ言い換える。
2. 文脈を読む: プロジェクトのドメイン、アーキテクチャ、既存テスト、依存関係を必要な範囲で確認し、局所的には正しいがプロジェクトに合わないテストを避ける。
3. 戦略を設計する: コードを書く前に、テストレベル、単体テストの境界、実物のまま使う依存関係、置き換える依存関係、検証方法を決める。
4. ケースを設計する: 具体的なケース、入力、操作、外から確認できる期待結果、テストダブルの役割を整理する。
5. 実装する: ローカル規約に従いながら、振る舞い重視の意図を保ってテストを書く。コードがテストしにくい場合は、テスト専用の逃げ道ではなく本番モデルも改善するリファクタリングを優先する。
6. セルフレビューする: 実装したテストが、目的、文脈、戦略、設計と合っているか確認する。

## 実行時資料

`references-ja/` は、別の参照表ではなく、現在のワークフロー工程を深掘りするために使う。
その工程について詳細な助言を出す前に、対応するファイルを読む。

| 工程 | 参照ファイル                         | 使う場面                                                     |
| ---- | ------------------------------------ | ------------------------------------------------------------ |
| 1    | `references-ja/01-purpose.md`        | テストが存在すべき理由と、ルールの強さを確認する。           |
| 2    | `references-ja/02-context.md`        | ドメイン、アーキテクチャ、依存関係、既存テストの文脈を読む。 |
| 3    | `references-ja/03-test-strategy.md`  | テストレベル、境界、依存関係の扱い、検証方法を選ぶ。         |
| 4    | `references-ja/04-test-design.md`    | 具体的なケース、アサーション、テストダブルの役割を設計する。 |
| 5    | `references-ja/05-implementation.md` | テストと安全なテスタビリティ改善を実装する。                 |
| 6    | `references-ja/06-self-review.md`    | 目的、文脈、戦略、設計に照らして結果をレビューする。         |

英語で出力する場合や英語文書を編集する場合は、対応する `references/` 側のファイルを使う。

## レビューモード

ユーザーがレビューを依頼した場合も、別のチェックリストへ切り替えず、同じワークフローを圧縮して使う。

1. 依頼、差分、コード、既存テストから、テストの目的を推定する。
2. 振る舞いと境界を理解できる範囲で、本番コードとテストコードの文脈を読む。
3. 選ばれた戦略が、振る舞いとリスクに合っているか確認する。
4. アサーションが、実装詳細ではなく振る舞いを確認しているか見る。
5. 実装が読みやすく、決定的で、保守しやすいか確認する。
6. 実際に問題がある場合は、指摘事項から始める。違反している原則、リスク、最小限の有効な修正方針を含める。

重大な問題がない場合は、その旨を明確に伝える。
確認できていない文脈、不明確な本番契約、未実行のテストなど、信頼度に影響する場合だけ残るリスクに触れる。

## 保守資料

`maintenance-ja/` と `maintenance/` は、このスキルを保守するときに読む資料である。
通常の単体テスト支援では読まない。
このスキルを編集する、ルール構造を変える、参照元との対応を確認する、設計背景を見直す場合にだけ使う。

このスキルを編集するときは、対応するファイルの意味を揃える。

- `references/` と `references-ja/` は、実行時資料として揃える。
- `maintenance/` と `maintenance-ja/` は、保守資料として揃える。

## 出力

新しいテストまたは変更したテストについては、テストの目的、関連するプロジェクト文脈、テスト戦略、具体的なテストケース、実装変更、レビュー結果を示す。
詳細度はタスクの大きさに合わせる。

レビューでは、指摘事項を重要度順に示す。
振る舞い、リファクタリング耐性、可読性、決定性、保守コストに影響しない限り、好みの問題を欠陥として扱わない。

ユーザーが別言語を明示しない限り、ユーザーの依頼言語で出力する。
