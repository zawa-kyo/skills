# 目的

## テストの目的を定める

Priority: Essential。
Trade-off: 価値がはっきりしないテストは、改善するか、別のテスト種別へ移す。不要なら削除する。

自動テスト全体の目的は、プロダクトの持続的な成長を支えることである。
単体テストは、そのうち小さな振る舞いを高速で決定的に検証し、リファクタリングを支えるためのテストである。

結合テストは、複数のコンポーネントや外部境界が正しく連携するかを確認する。
E2E テストは、代表的なユーザー経路がシステム全体を通して成立するかを確認する。
単体テストにすべての保証を負わせず、守りたいリスクに合うテスト種別を選ぶ。

単体テストは、重要なリグレッションを検出し、リファクタリングを支える場合に価値を持つ。
頻繁に実行でき、読みやすいことも必要である。

テストを無料の資産として扱わない。プロダクションコードと同じように、テストコードにも保守コストが発生する。

- 読む、実行する、失敗を調査する、仕様変更に合わせて更新する必要がある。
- 信頼できる状態に保たれていないテストは、保守者の判断を鈍らせる。
- 守る価値が説明できないテストは、資産ではなく負債になりやすい。

テストを設計またはレビューする前に、そのテストが何を守るためのものかを明確にする。
「カバレッジを上げる」「テストがないから追加する」だけでは、テストを追加する理由として不十分である。
守るべき振る舞い、リグレッションリスク、保守上のメリットが見える場合に、はじめてテストを追加する。

良い目的文は、テストケースとアサーションを選べる程度に具体的である。

- BAD: `DiscountService` のカバレッジを上げる
- GOOD: 期限切れクーポンが拒否され、カート合計が変わらない規則を守る
- BAD: ユーザーリポジトリをテストする
- GOOD: 既存メールアドレスを再登録したときのアプリケーション上の振る舞いを守る

壊れたときに誰にとって何が問題になるかを言えない場合は、テストを書く前に立ち止まる。
次にすべきことは、ドメインコンテキストを読むこと、別のテスト種別へ移すこと、または専用の単体テストは不要だと判断することのいずれかである。

## 品質特性

Priority: Essential。
Trade-off: すべての品質特性を最大化する単一のテストはない。振る舞いの重要度とリスクに応じて選ぶ。

単体テストは次の観点で評価する。

- リグレッションに対する保護: 重要な振る舞いが壊れたときに失敗する。
- リファクタリング耐性: 実装詳細が変わっただけでは失敗しない。
- 迅速なフィードバック: 頻繁に実行できるほど軽い。
- 保守性: 読みやすく、目的がはっきりしており、更新コストが低い。

これらは単なるキーワードではなく、トレードオフを考えるための軸である。

たとえば、リスクの低いアクセサに専用の単体テストは要らないことがある。
一方で、リグレッションの影響が大きい業務ルールには、カバレッジが十分でも複数の例が必要になることがある。

これらの品質特性は、次のようなトレードオフとして説明できる。

- 純粋な価格計算ルールは、リグレッション保護、リファクタリング耐性、迅速なフィードバック、保守性を高くしやすいため、単体テストの有力な対象になる。
- 多数のモックを使うコントローラテストは高速に動いても、リファクタリング耐性と保守性を失いやすい。
- getter を確認するだけのテストは高速で保守しやすくても、リグレッション保護の価値は低いことが多い。

## カバレッジ指標

Priority: Recommended。
Trade-off: カバレッジは未テスト領域を示せるが、テスト品質は保証しない。

カバレッジは見落としを探す手がかりとして使い、目標そのものにしない。
カバレッジが低いことは、重要なコードがテストされていない可能性を示している。
カバレッジが高いことは、振る舞いが正しく検証されていることの証明にはならない。

カバレッジの値を満たすためだけにテストを書いてはならない。

ユーザーがカバレッジを求めている場合は、カバレッジを修正すべき候補を探す指標として扱い、その後に振る舞いでテストを選ぶ。
分岐を通っていても外から確認できる結果を検証していないテストは、カバレッジを増やしているだけで、振る舞いを守っていない。

## 目的を確認する観点

コンテキストや設計へ進む前に、次を確認する。

- 守る価値がある振る舞い、ルール、リスクは何か。
- 壊れたときに、ユーザー、ドメインエキスパート、保守者、依存システムの誰が困るか。
- そのリスクは単体テストで扱うべきか、別のテスト種別で扱うべきか。
- その振る舞いに許容できる保守コストはどの程度か。
- そのテストが資産ではなく技術負債になる条件は何か。
