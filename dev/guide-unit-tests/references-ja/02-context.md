# 文脈の把握

## ドメインとアーキテクチャを読む

Priority: Essential。
Trade-off: 小さな独立関数では、最小限の文脈で足りる場合がある。ドメイン上の振る舞いでは、文脈を飛ばすと誤ったテストになりやすい。

振る舞いがドメインの意味、アーキテクチャ境界、既存のテスト方針に依存する場合は、クラスやメソッドだけを見て単体テストを設計しない。

次を答えられる程度にプロジェクトの文脈を確認する。

- どのドメイン上の振る舞いや不変条件が関係しているか。
- その判断は、ドメイン、アプリケーション、アダプタ、UI、インフラ、またはプロジェクト固有のどの層が持つべきか。
- 安定したプロセス内の協力オブジェクトはどれか。
- 共有依存、不安定な依存、プロセス外の依存はどれか。
- 既存テストは、命名、フィクスチャ、ビルダー、テストダブルをどう使っているか。
- 直接的な単体テストが不適切になるアーキテクチャ上の制約はあるか。

文脈を読むときに、依存関係を分類する。

- 共有依存: 共有データベースやグローバルな可変シングルトンのように、テスト間で状態が漏れ得る依存。
- 揮発性依存: 現在時刻、乱数、リモートサービスのように、非決定的または環境依存の振る舞いを持つ依存。
- 安定したプロセス内依存: 同じプロセス内にある通常のドメインオブジェクト、値オブジェクト、パーサ、計算器、ポリシーオブジェクト。

デフォルトでは、共有依存と揮発性依存を制御し、安定したプロセス内の協力オブジェクトは実物のまま使う。
これにより、1クラスの実装構造ではなく、振る舞いに焦点を合わせやすくなる。

## テストしにくさを設計の手がかりにする

Priority: Recommended。
Trade-off: インフラや並行処理には本質的な難しさがある。すべての難しいテストがドメインモデルの問題を示すわけではない。

テストしにくいコードには、隠れた依存、混ざった責務、グローバル状態、過剰な制御、インフラの背後に閉じ込められたドメインルールが含まれていることがある。

モック、フラグ、テスト専用アクセサを増やす前に、設計を見直す手がかりとして扱う。

## 判断と副作用を分ける

Priority: Recommended。
Trade-off: 判断ロジックがほとんどない単純なコードを過剰に抽象化しない。

重要な判断は、可能な範囲で小さく決定的な中心へ移す。
副作用は外側の層に置き、結合テストや境界を対象にした少数の単体テストで扱う。

例として、ドメイン判断の中で暗黙の現在時刻を読むのではなく、必要な時刻値を渡す。

```typescript
function canRenew(subscription: Subscription, now: Date): boolean {
  return subscription.expiresAt > now && !subscription.cancelled;
}
```

時計を読む処理は外側のアプリケーションサービスに置ける。
規則そのものは決定的になり、出力ベースのアサーションでテストしやすくなる。

## 非公開メソッドではなく概念を抽出する

Priority: Recommended。
Trade-off: 抽出は、新しい概念に実際の責務と外から使える仕様がある場合にだけ有効である。

非公開の振る舞いが重要で複雑なら、非公開メソッドを直接テストするのではなく、名前を付けられる概念として抽出する。

## 文脈把握の出力

テスト戦略へ進む前に、実務上必要な粒度で次をまとめる。

- 振る舞いとドメイン上の意味
- 振る舞いを持つ層または境界
- 実物のまま使う依存関係
- 制御、フェイク化、またはモック化する依存関係
- テスト実装前または実装中に求められる設計改善
