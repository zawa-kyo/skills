# コンテキストの把握

## ドメインとアーキテクチャを読む

Priority: Essential。
Trade-off: 小さな独立関数では、最小限のコンテキストで足りる場合がある。ドメイン上の振る舞いでは、コンテキストを飛ばすと誤ったテストになりやすい。

振る舞いがドメインの意味、アーキテクチャ境界、既存のテスト方針に依存する場合は、クラスやメソッドだけを見て単体テストを設計しない。

次を答えられる程度にプロジェクトのコンテキストを確認する。

- どのドメイン上の振る舞いや不変条件が関係しているか。
- その判断は、ドメイン、アプリケーション、アダプタ、UI、インフラ、またはプロジェクト固有のどの層が持つべきか。
- 安定したプロセス内の協力オブジェクトはどれか。
- 共有依存、揮発性依存、プロセス外の依存はどれか。
- 既存テストは、命名、フィクスチャ、ビルダー、テストダブルをどう使っているか。
- 直接的な単体テストが不適切になるアーキテクチャ上の制約はあるか。

コンテキストを読むときに、依存関係を分類する。
このファイルでは、次の意味で用語を使う。

- 共有依存: 共有データベースやグローバルな可変シングルトンのように、テスト間で状態が漏れ得る依存。
- 揮発性依存: 現在時刻、乱数、リモートサービスのように、非決定的または環境依存の振る舞いを持つ依存。
- 安定したプロセス内依存: 同じプロセス内にある通常のドメインオブジェクト、値オブジェクト、パーサ、純粋な計算ロジック、ポリシーオブジェクト。

デフォルトでは、共有依存と揮発性依存を制御し、安定したプロセス内の協力オブジェクトは実物のまま使う。
これにより、1クラスの実装構造ではなく、振る舞いに焦点を合わせやすくなる。

## テストしにくさを設計の手がかりにする

Priority: Recommended。
Trade-off: インフラや並行処理には本質的な難しさがある。すべての難しいテストがドメインモデルの問題を示すわけではない。

テストしにくいコードは、設計上の問題を示していることがある。
たとえば、隠れた依存、混ざった責務、グローバル状態、過剰な制御、インフラの背後に閉じ込められたドメインルールが含まれている場合である。

その場合は、モック、フラグ、テスト専用アクセサを増やす前に、具体的な方針とともにリファクタリングを提案する。
大規模なリファクタリングが必要になる場合は、コストとリスクを説明したうえで、境界を絞った妥協案を選んでもよい。
ただし、妥協によって残る設計上の問題はユーザーに伝える。

テストしにくさを常に欠陥とみなすのではなく、設計を見直す手がかりとして扱う。

## 判断と副作用を分ける

Priority: Recommended。
Trade-off: 判断ロジックがほとんどない単純なコードを過剰に抽象化しない。

ドメイン的に重要なロジックは、可能な範囲でアーキテクチャの中心部分に置く。
フレームワーク、I/O、外部サービス、時刻、乱数などの影響を直接受けにくくすると、単体テストで振る舞いを確認しやすくなる。

副作用は外側の層に置き、結合テストや境界を対象にした少数の単体テストで扱う。
ただし、プロジェクトがレイヤードアーキテクチャなど別の構造を採っている場合は、その境界と責務に合わせる。
明示的な設計方針が見つからない場合は、クリーンアーキテクチャやオニオンアーキテクチャのように、ドメインロジックを外部詳細から遠ざける考え方を出発点にしてよい。

### 具体例

ドメイン判断の中で暗黙の現在時刻を読むのではなく、必要な時刻値を渡す。

```typescript
function canRenew(subscription: Subscription, now: Date): boolean {
  return subscription.expiresAt > now && !subscription.cancelled;
}
```

時計を読む処理は外側のアプリケーションサービスに置ける。
規則そのものは決定的になり、出力ベースのアサーションでテストしやすくなる。

## プライベートメソッドではなく概念を抽出する

Priority: Recommended。
Trade-off: 抽出は、新しい概念に実際の責務と外から使える仕様がある場合にだけ有効である。

プライベートメソッドを直接テストしない。
プライベートな振る舞いが重要で複雑なら、外から使える仕様を持つ概念として抽出する。

## コンテキスト把握の出力

テスト戦略へ進む前に、実務上必要な粒度で次をまとめる。

- 振る舞いとドメイン上の意味
- 振る舞いを持つ層または境界
- 実物のまま使う依存関係
- 制御、フェイク化、またはモック化する依存関係
- テスト実装前または実装中に求められる設計改善
