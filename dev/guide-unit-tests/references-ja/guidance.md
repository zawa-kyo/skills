# 単体テストの指針

## 課題と状況

振る舞い、リグレッションのリスク、単体テストで守れる理由、別の検証手段へ割り当てるリスクを示す。
単体テストは、頻繁に実行できる速度で動き、ほかのテストから独立している必要がある。
また、制御できない共有状態やプロセス外の状態を避け、意味のある結果を観測できるようにする。

次を判断できる範囲で状況を確認する。

- ドメイン上の振る舞いと不変条件
- 判断を担うコード
- 確立されたアーキテクチャとテスト規約
- 安定したプロセス内の協力オブジェクト
- 共有依存、揮発性依存、プロセス外の依存関係
- テストを実質的に妨げている設計上の問題

テストしにくさは、隠れた依存関係、混在した責務、グローバル状態、副作用の中に埋もれた判断を示すことがある。
調査する根拠にはなるが、アーキテクチャが誤っていることを自動的に意味しない。

明示的なアーキテクチャがない場合は、名前、依存関係、呼び出し方向、既存のテストから責務を読み取る。
それでも設計意図が曖昧で、プロダクションコードの変更に影響する場合は、考えられる解釈をユーザーと確認する。

## 境界と依存関係

単体テストの対象は振る舞いであり、必ずしも一つのクラスやメソッドではない。
ドメインロジックが中心の場合は、安定した協力オブジェクトを実物のまま使い、一まとまりの振る舞いをテストする方法が有力な出発点になる。
リポジトリの規約、フレームワークの制約、不具合が生じた箇所の特定、協力オブジェクトの不安定さに理由がある場合は、一つのクラスに絞ったテストも妥当である。

現在時刻、乱数、共有データベース、ファイルシステム、リモートサービス、変更可能なグローバル状態、プロセス外のメッセージングなどの共有依存と揮発性依存は制御する。
別のクラスであることだけを理由に、安定したプロセス内の協力オブジェクトを置き換えない。

これらは、一貫した既存の設計を上書きする規則ではなく、プロジェクトの根拠と照らし合わせる既定値として扱う。

同じ契約を表せる場合は、次の順に観測方法を検討する。

1. 戻り値や副作用のない結果
2. 外部から確認できる状態
3. 意味のある境界との通信

通信自体が振る舞いである場合は、やり取りを検証する。
問い合わせ方が契約に含まれない限り、スタブがどのように呼ばれたかは検証しない。

## ケースとアサーション

振る舞い、関係する入力や事前条件、操作、期待する結果を示す少数のケースを設計する。
実装上の分岐を列挙するより、契約、要求、不変条件、境界、意味のある例を優先する。

公開契約でない限り、非公開のアルゴリズム、ヘルパー呼び出し、中間状態、呼び出し順を検証しない。
価値のある非公開ロジックが独立した責務を持つ場合は、テストのために非公開メンバーを公開せず、公開契約を持つ概念として切り出すことを検討する。

外部から見える影響を守る必要がある場合は、意味のある境界との通信をモックで検証する。
一つのクラスだけをテストするために、通常のドメイン上の協力オブジェクトまでモックにしない。

## 実装

- 振る舞いが伝わる範囲で、リポジトリのフレームワーク規約と命名規約に従う。
- 一つのテストでは、一まとまりの振る舞いを一度実行する。
- 流れが分かりやすくなる場合は Arrange、Act、Assert を使う。構造が明らかならコメントは不要である。
- アサーションのロジックは単純にし、プロダクションコードのアルゴリズムから独立させる。
- 固定された入力と期待する結果だけが変わる場合は、パラメータ化テストを使う。
- 技術的な準備にはビルダーやファクトリを使い、シナリオに関係する値はテスト内で見えるようにする。
- テスト専用の分岐、公開 setter、変更可能なグローバル状態を追加せず、本番で使う契約も緩めない。

テスト容易性のためのリファクタリングがプロダクションコードの設計も改善する場合は、その変更を検討する。
理想的な変更が依頼範囲を超える場合は、大きな選択肢を説明した上で、ユーザーと範囲を絞った対応を選ぶ。

## レビュー

次の順に確認する。

1. 割り当てられた振る舞いとリスクを守っているか。
2. 境界がプロダクションコードの責務と、確認した設計意図に合っているか。
3. 依存関係を制御しても、テスト対象の仕組みが残っているか。
4. アサーションが実装手順ではなく、意味のある振る舞いを観測しているか。
5. テストダブルが有用な役割に限られているか。
6. 結果が決定的で、読みやすく、単独で実行できるか。
7. その場で修正するより、削除、再割り当て、プロダクションコードの改善が適切ではないか。

違反している原則、具体的なリスク、適用条件、最小限の有効な修正を報告する。
