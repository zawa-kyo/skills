# 自動テストを設計する

## 責務

テストレベルを選ぶ前、または複数のレベルにまたがる次の判断を扱う。

- テストが必要な理由と、問題となる失敗
- その失敗を検出するために通すべき境界
- 信頼性、フィードバック速度、原因調査、保守コストのバランス
- 各テストレベルへ割り当てる責務
- 別のテストレベルや検証手段へ残すリスク

望ましいテスト構成、カバレッジ目標、アーキテクチャを起点にしない。
テストピラミッド、テスティングトロフィー、テスト本数は、必須の形ではなく判断材料として扱う。

## 共通原則

- 実装構造やカバレッジ値ではなく、価値のある観測可能な振る舞いを守る。
- テストが実際に通す仕組みと依存関係を超えて、保証できる範囲を広げない。
- 実行、環境、原因調査、保守を合わせたコストが最も小さい、信頼できるテストを選ぶ。
- 広いテストは、狭いテストでは得られない信頼を追加できる場合に使う。
- 意図的に残すリスクを明示する。すべてのリスクを自動化する必要はない。

## ユーザーとの認識合わせ

利用できる場合は、プロダクションコード、アーキテクチャ、依存関係、既存のテスト、リリース上の制約、過去の障害を確認する。
確認できた事実と仮定を分ける。

複数の戦略が成り立つ場合は、次の順に進める。

1. 採用可能な境界や責務分担を示す。
2. 各案が保証すること、保証しないこと、必要なコストを説明する。
3. リポジトリとユーザーの優先事項に基づいて一案を推奨する。
4. 影響の大きな仮定や変更は、実装前にユーザーと確認する。

テスト戦略の検討範囲は依頼に合わせる。
指定されたテストレベルで問題となる失敗を検出できる場合は、振る舞い、リスク、境界を簡潔に確認する。
その後、テストスイート全体の分析を強制せず、専門スキルへ委ねる。

## 手順

1. 重要な振る舞い、リグレッション、変更に伴うリスクを明らかにする。
2. リポジトリを調べ、関係する制約と不明点を特定する。
3. 候補となる境界を、エントリーポイント、含める範囲、依存関係の再現度、配置方法、観測する結果、運用コストで表す。
4. リスクを守れる最小の境界へ割り当てる。ユーザーの優先事項によって答えが変わる場合は選択肢を比較する。
5. 抜け、同じ信頼性を重複して確認している箇所、遅いフィードバックへの偏り、実装の詳細への結合を確認する。
6. テスト課題を作り、詳しい作業を対応する専門スキルへ委ねる。

選択、テストスイートのレビュー、引き継ぎの詳細は `references-ja/guidance.md` を読む。
英語で出力する場合や英語文書を扱う場合は `references/guidance.md` を使う。

## 専門スキルへの委譲

- 制御できない共有状態やプロセス外の状態を避け、高速かつ決定的に振る舞いを確認できる場合は `guide-unit-tests` を使う。
- 実際のコンポーネント、インフラ、シリアライズ、フレームワークの接続、制御されたプロセス外の依存関係との連携が信頼性に必要な場合は `guide-integration-tests` を使う。
- プロジェクトが定める E2E テストの境界を通して、利用者から見える代表的な一連の振る舞いやシステム全体の接続を確認する場合は `guide-e2e-tests` を使う。

振る舞い、リスク、境界、依存関係、観測する結果、制約、保証しない範囲を示してから委ねる。
複数のレベルにまたがる依頼では、課題全体を調整し、各専門スキルにはそのレベル固有の作業だけを任せる。

## 出力

次を報告する。

- 確認できた事実、仮定、関係する不明点
- 守る振る舞いとリスク
- 選んだ境界、または比較した選択肢
- 実物のまま使う、制御する、置き換える、利用できない依存関係
- 観測する結果と得られる信頼性
- 運用と保守のトレードオフ
- 各専門スキルへ委ねる責務
- 別の検証手段へ残すリスク

ユーザーから指定がない限り、ユーザーが使った言語で出力する。
