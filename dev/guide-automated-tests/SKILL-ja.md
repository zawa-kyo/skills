# 自動テストの戦略を組み立てる

## 責務

テストレベルを選ぶ前、または複数のレベルにまたがる次の判断を扱う。

- 検証が必要な理由と、問題となる失敗
- その失敗を検出するために必要な根拠
- その根拠を得られる境界や検証方法
- 信頼性、原因調査、実行頻度、作成と保守のコストのバランス
- 別のテストや対策で扱うリスクと、承知の上で未検証とするリスク

ユーザーが単体、結合、E2E のいずれかを指定し、その境界で問題となる失敗を検出できる場合は、専門スキルを直接使う。
境界が不明確な場合、複数のレベルにまたがる場合、または指定された境界を見直す必要がある場合は、このスキルを使う。

望ましいテスト構成、カバレッジ目標、アーキテクチャ、三つのテストレベルによる分類を起点にしない。
テストピラミッド、テスティングトロフィー、テスト本数は、必須の形ではなく判断材料として扱う。

## ユーザーとの認識合わせ

利用できる場合は、プロダクションコード、アーキテクチャ、依存関係、既存のテストや対策、リリース上の制約、過去の障害を確認する。
確認できた事実と仮定を分ける。

複数の方法が成り立つ場合は、次の順に進める。

1. 採用可能な方法や境界を示す。
2. 各案から分かること、分からないこと、必要なコストを説明する。
3. リポジトリとユーザーの優先事項に基づいて一案を推奨する。
4. 影響の大きな仮定や変更は、実装前にユーザーと確認する。

戦略を検討する深さは依頼に合わせる。

## 手順

1. 重要な振る舞い、リグレッション、変更に伴うリスクを明らかにする。
2. リポジトリを調べ、関係する制約と不明点を特定する。
3. 問題となる失敗を検出するために必要な根拠を定める。
4. 信頼性、原因調査、実行頻度、作成と保守のコストから、採用可能な検証方法を比較する。
5. ユーザーが示した優先事項のバランスを最もよく満たす方法または組み合わせを選ぶ。
6. 依頼に応じて、既存の検証にある抜け、根拠のない保証、価値のない重複、遅いフィードバックへの偏り、実装の詳細への結合を確認する。
7. 専門スキルの責務に明確に該当する作業は委ねる。それ以外の方法は、新しい分類を作ったり三つのテストレベルへ押し込んだりせず、このスキルで検討する。

詳しい判断基準、テストスイートのレビュー、引き継ぎは `references-ja/guidance.md` を読む。
英語で出力する場合や英語文書を扱う場合は `references/guidance.md` を使う。

## 専門スキルへの委譲

単体、結合、E2E のいずれかに明確に該当する課題を、`guide-unit-tests`、`guide-integration-tests`、`guide-e2e-tests` の対応するスキルへ委ねる。
委ねる前に、`references-ja/guidance.md` で定義する選択基準を使い、テスト課題を作る。
どの専門スキルにも明確に該当しない場合は、確認した状況から判断し、委ねずに扱う。

## 出力

確認した根拠と仮定、選んだ検証方法または比較した選択肢、信頼性とコストのバランス、委ねた作業、残るリスクを報告する。
詳しさはタスクに合わせる。

ユーザーから指定がない限り、ユーザーが使った言語で出力する。
