# テスト戦略の指針

## 名前より先に境界を表す

候補となるテストを次の観点で表す。

- エントリーポイント
- 含める振る舞い、コンポーネント、プロセス、インフラ
- 実物のまま使う、制御する、置き換える、利用できない依存関係
- 同一プロセス内、別に起動、デプロイ済みなどの配置方法
- 観測する結果
- 実行、環境、原因調査、保守のコスト

単体テスト、結合テスト、E2E テストは、これらの観点を組み合わせた代表的な区分であり、完全な分類ではない。
実際の境界を明らかにした後で、プロジェクトの用語に合わせる。

## 各テストレベルでしか得られない信頼性を割り当てる

問題となる仕組みを含む境界を選ぶ。

- 制御できない共有状態やプロセス外の状態に依存せず、高速かつ独立して振る舞いを確認できる場合は、単体テストが候補になる。
- 実際の連携、インフラに固有の性質、シリアライズ、フレームワークの接続、制御されたプロセス外の依存関係が問題となる場合は、結合テストが候補になる。
- 利用者から見える一連の振る舞い、外部エントリーポイント、システム全体の接続が問題となる場合は、E2E テストが候補になる。

同じ詳細をすべてのテストレベルで繰り返さない。
広いテストは、狭いテストでは確認できない振る舞いを守るために使う。

## テストスイートを確認する

1. 重要な振る舞いと失敗リスクを列挙する。
2. 各リスクを、検出する予定のテストや別の対策へ対応付ける。
3. その検証が、実際に問題となる仕組みを含むか確認する。
4. 守られていないリスクと、テスト境界を超えた保証を見つける。
5. 別のテストと同じ内容しか確認していない、重複したテストを見つける。
6. フィードバック時間、環境コスト、原因調査が開発手順に合うか確認する。

テスト本数、実行時間、カバレッジは、調査対象を見つける材料にはなる。
守るリスクの価値までは証明しない。

## テスト課題を作る

専門スキルへ次を渡す。

- 振る舞いと失敗リスク
- 選んだ境界と理由
- エントリーポイントと含める範囲
- 依存関係の扱い
- 観測する結果
- 必要なシナリオ
- 実行と保守の制約
- 別の検証手段へ割り当てたリスク

専門スキルは、実装前にローカルコードとフレームワークの規約を確認する。
