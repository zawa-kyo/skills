# 本質的なコードレビュー

## 目的

コード変更が、既存の設計に沿って根本原因を解決しているかを確認する。
観測された失敗を隠すだけの特殊ケース、重複ロジック、過剰なガード、不要な抽象化など、AI 生成コードで起こりやすい場当たり的な修正を見抜く。

## ワークフロー

1. レビュー対象と範囲を特定する。指定がなければ、現在の Git 差分をステージング済みと未ステージングに分けて確認する。レビュー中はワークツリーと index を変更しない。
2. 周辺コード、テスト、ドキュメントを読み、対象の振る舞い、既存の不変条件、公開契約、責務の境界、ローカルな設計パターンを理解する。
3. 提示された原因と修正案を仮説として扱う。失敗の再現、コード経路、テスト、ログ、契約など、利用できる根拠から問題の仕組みを確認する。
4. 変更された経路と、その振る舞いに責任を持つ境界を特定する。
5. 通常のリスクを確認する。バグ、リグレッション、データ損失、セキュリティ、性能、API 契約、テスト不足を対象にする。
6. 本質性を確認する。
   - 根本原因を解決しているか。失敗を抑え込んでいるだけではないか。
   - 既存のルールや責務の境界を使っているか。特定の入力だけを特別扱いしていないか。
   - 複雑さや重複を減らしているか。分岐、フラグ、リトライ、待機、広い例外処理、型のごまかしなどを足していないか。
   - 呼び出し側の振る舞いと、実装を保守する理由が明確か。
7. 具体的な箇所と根拠のある問題だけを指摘する。分岐やガードなどの形だけで欠陥とみなさない。仮説にとどまるものは未解決の問いとして分け、問題がなければそう明示する。

## テスト

テストの境界やテストレベルの選択自体が問題になる場合は、`guide-automated-tests` または対応する専門スキルを使う。テスト形式の好みだけは指摘しない。

## 出力

重大度順に、ファイルと行、具体的なリスク、根拠、根本原因を解決して責務境界や不変条件を回復する最小の修正方針を示す。
指摘として断定できない前提、未解決の問い、実行しなかった確認は、必要な場合だけ後に分けて書く。
ユーザーが明示的に求めない限り、コードは変更しない。ユーザーの言語で報告する。
