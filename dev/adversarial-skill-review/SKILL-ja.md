# Adversarial Skill Review

## 目的

エージェントスキルを完了扱いにする前に、敵対的レビューで改善する。レビュー担当は新鮮で懐疑的な視点からスキルを読み、正しさの欠落、要件漏れ、発動条件の失敗、安全でないスコープ拡大、評価の穴を探す。この作業は文体レビューでも、プロンプトをむやみに膨らませる作業でもない。

目的は、あらゆる場合に備えた防御的な指示を増やすことではなく、そのスキルが意図したワークフローを本当に支えられるかを確かめることにある。

## 使う場面

エージェントスキルやスキルパッケージに触れる作業では、このスキルを使う。特に次の場合に使う。

- 新しい `SKILL.md` を作る
- スキルのワークフロー、発動説明、同梱リファレンスを変更する
- 対になる `SKILL.md` と `SKILL-ja.md` を変更する
- スキルの評価プロンプトを追加または変更する
- スキルに関する README やパッケージメタデータを更新する
- 長い自律的なスキル編集作業を終える

通常のコードレビューを求められている場合は、対応するコードレビュー用スキルを使う。スキルの作成や改善を求められている場合は、`skill-creator` の終盤に行う補助的なレビューとして使う。

## レビュー入力

レビュー担当が成果物を独立に判断できる、最小限の入力を集める。

- スキル作業の目的または計画
- 現在の差分、または変更されたスキルファイル
- 期待する発動条件
- スキルに期待する出力や振る舞い
- 評価プロンプト、アサーション、受け入れ基準があればそれら
- 日英同期など、リポジトリ固有のルール

受け入れ基準に含まれる場合を除き、実装時の推論はレビュー担当に渡さない。新鮮なレビューの価値は、成果物そのものを見て判断できる点にある。そこに至った経緯に引っ張られにくくなるためである。

## ワークフロー

1. どのスキル作業をレビューするのかを明示する。
2. 何を指摘事項として扱うかを明示する。
3. 可能であれば、新しいサブエージェント文脈で独立レビューを実行する。
4. 正しさ、明示された要件、発動条件、安全性、保守性、評価品質に影響する抜けだけを報告するよう依頼する。
5. 文体の好み、推測上のエッジケース、広い再設計案は、明示された目的を損なわない限り任意扱いにする。
6. スコープ内の実行可能な指摘を修正する。
7. 意味のある修正後に、敵対的レビューを再実行する。
8. 残したリスクや未検証の確認事項を報告する。

## レビュー用プロンプトの雛形

新しいサブエージェントや独立レビュー担当には、次のようなプロンプトを使う。

```text
Review the skill work below from a fresh context.

Work to check:
<name the skill or package>

Goal or plan:
<summarize the intended behavior, trigger conditions, and scope>

Review material:
<diff, changed files, or paths to inspect>

Report findings only when they affect correctness, stated requirements,
trigger behavior, safety, maintainability, bilingual sync, or evaluation quality.
Do not report style preferences, speculative edge cases, or broader redesign ideas
unless they make the skill fail its stated purpose.

For each finding, include:
- severity
- evidence from the reviewed material
- why it affects the stated goal
- the smallest useful correction

If there are no blocking findings, say so clearly and mention any verification gaps.
```

## 確認観点

次の問いに照らして成果物を確認する。

- `description` は、そのスキルを使うべき実際のユーザー状況で発動しそうか。
- 本文は広い助言ではなく、実行できるワークフローになっているか。
- スキルはスコープを保っているか。別のスキルが扱うべき隣接問題まで解こうとしていないか。
- 必要な対訳ファイル、メタデータ、README、パッケージマニフェストは更新されているか。
- 日英対応のスキルでは、`SKILL.md` と `SKILL-ja.md` が意味を合わせつつ、それぞれの言語で自然に書かれているか。
- 実在しないリファレンスやスクリプトを参照していないか。
- 評価プロンプトやアサーションは、簡単すぎるケースや無関係なケースではなく、中核的な振る舞いを見ているか。
- ツール、サブエージェント、ファイル、文脈が使えない場合に何をするかが書かれているか。
- 過剰設計、不要なファイル変更、安全でない操作、根拠のない安心につながる指示はないか。

## 指摘の扱い

修正前に各指摘を分類する。

- **実行対象：** 明示された目的に影響し、修正範囲が明確である。修正する。
- **任意：** 有用な改善ではあるが、正しさや明示されたスコープには必須ではない。次の判断材料になる場合だけ伝える。
- **不採用：** 文体の好み、通常の利用条件では起こらないエッジケース、スキルを肥大化させる広い再設計である。ユーザーが判断材料を必要とするときだけ、適用しなかった理由を述べる。

敵対的レビューの指摘をすべて追わない。良いレビュー担当は、もっともらしいが修正に値しない懸念も出すことがある。実装担当はスキルの焦点を保ち、起こりにくい誤用に備えるだけの指示を増やさない。

## 出力

ユーザーの言語でレビュー結果を報告する。

- 修正した指摘
- 残したリスクとして受け入れた指摘
- 実装しなかった任意案
- 実行した確認。新しいサブエージェントによるレビューを実際に使ったかも含める

新しいサブエージェントや独立レビュー担当を使えない場合は、インラインの敵対的レビューであることを明示し、その分だけ信頼度を下げて伝える。
